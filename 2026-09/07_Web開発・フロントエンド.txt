### ドメインモデル貧血症はなぜ生まれるのか — Decision パターンで DDD トリレンマを解く

さて、まず最初にご紹介するのは、Zennの記事「ドメインモデル貧血症はなぜ生まれるのか — Decision パターンで DDD トリレンマを解く」です。この記事は、Go言語を使っていて、ドメイン層にロジックがなかなか集まらないと感じている方、DDD（ドメイン駆動設計）の戦術的パターンを導入しても、結局ドメインの外側にロジックが漏れてしまうという悩みを抱えている方に向けた内容になっていますね。

皆さんは「ドメインモデル貧血症（Anemic Domain Model）」という言葉を聞いたことがありますか？ これは、DDDの文脈でよく語られるアンチパターンの一つで、ドメイン層にあるはずのビジネスロジックが、エンティティ（実体）やバリューオブジェクト（値オブジェクト）ではなく、サービス層やアプリケーション層といった別の場所に散らばってしまう状態を指します。ドメインオブジェクトがただのデータコンテナになってしまい、自律的な振る舞いを持たないことから「貧血症」と呼ばれるわけですね。これ、特に静的型付け言語を使っていると陥りやすいんですよ。なぜかというと、ドメインロジックを実行するために、データベースへのアクセスや外部API呼び出しといったインフラ層の機能が必要になる場面が多々あるからです。これらのインフラ依存をドメイン層に持ち込んでしまうと、ドメイン層が「純粋なビジネスロジック」に集中できなくなり、テストも難しくなります。しかし、インフラ層にロジックを委ねると、今度はドメインモデルがただのデータになってしまう。このジレンマが、記事で言うところの「構造的なトリレンマ」なんですね。

この記事では、このトリレンマを解決するアプローチとして「Decisionパターン」というものを提案しています。これは、ドメインモデルが何らかの判断を行う際、その判断の結果として「次に何が必要か」「どのような副作用が考えられるか」といった情報を、具体的な型として返す、という考え方です。例えば、ユーザー登録の際に「このユーザー名は利用可能か？」という判断が必要だとして、その結果として「利用可能です、このまま登録に進んでください」という情報や、「利用できません、代替案を提示します」という情報を、ドメインモデル自身が決定して型として返す。そうすることで、ドメインモデルは自身で完結した判断ロジックを持ちつつ、実際にデータベースを更新したり、メールを送信したりといったインフラ側の処理は、ドメインモデルから返されたその「Decision」に基づいて、外部の層が行うことができるようになります。

なぜこのアプローチが重要かというと、ドメインモデルが本当にビジネスのコアな部分に集中できるようになるからです。インフラの都合に引きずられることなく、純粋なビジネスルールを表現し、テストしやすくなる。これは、長期的に見てシステムの保守性や拡張性を高める上で非常に大きなメリットです。特にGo言語のような環境でDDDを実践している方にとっては、`context.Context` や `error` といったGo特有の要素をドメイン層にどう持ち込むかという問題に対する、一つの洗練された解答になりうるんじゃないかなと思いますね。ドメインモデルがよりパワフルで、生き生きとしたものになるための、具体的なヒントが詰まった良記事でした。

### WebエンジニアのためのReact Native + NativeWind v5事始め — Webの常識が通用しない18のポイント

続いてのニュースは、React Native と NativeWind に関するZenn記事です。「WebエンジニアのためのReact Native + NativeWind v5事始め — Webの常識が通用しない18のポイント」というタイトルからもわかる通り、Webフロントエンドの知識を活かしてモバイルアプリ開発に挑戦しようとするエンジニアが、どんなところでつまずきやすいかを具体的に教えてくれる内容ですね。

近年、Webエンジニアがモバイルアプリ開発に参入するケースが増えています。その際によく採用されるのが、Web開発で培ったReactの知識をそのまま活用できるReact Nativeです。さらに、スタイルについては、ユーティリティファーストCSSフレームワークであるTailwind CSSの記法をReact Nativeでも使えるようにするライブラリ「NativeWind」を組み合わせることで、Webとモバイルでスタイリングの知識を共有しやすくなります。しかし、記事が指摘するように、Webの常識がそのままモバイルに通用するわけではありません。React Nativeは最終的にネイティブのUIコンポーネントに変換されるため、WebのHTML要素やCSSの挙動とは異なる点が多く、それが時に混乱を招きます。

例えば、Webでは`className`属性を使ってCSSクラスを適用しますが、React Nativeでは`style`プロパティにJavaScriptオブジェクトでスタイルを渡すのが基本です。NativeWindを使えば`className`のような記法で書けますが、それはあくまで内部的にNativeWindがReact Nativeのスタイルオブジェクトに変換しているためです。また、CSSのプロパティについても違いがあります。Webでは`display: flex`以外にも`block`や`inline-block`といった概念がありますが、React NativeのViewコンポーネントはデフォルトでFlexboxレイアウトが適用されており、Webのそれとは異なる振る舞いをします。単位もそうですね。Webでは`px`や`rem`を使いますが、React Nativeでは「密度非依存ピクセル（dp）」という概念が基本で、数値をそのまま指定することが多いです。さらに、WebのCSSでは親要素から子要素へ`font-size`や`color`が継承されますが、React Nativeでは基本的に継承されず、特にTextコンポーネント以外に文字関連のスタイルを適用しても効かない、といったことが挙げられます。疑似クラスや複雑なセレクタ、グローバルなスタイルといったWebのCSSでは当たり前の概念も、NativeWindとReact Nativeの世界ではそのままでは使えません。

この記事がなぜ重要かというと、WebエンジニアがReact Native + NativeWindでモバイル開発を始める際の、具体的な落とし穴と解決策を網羅的に提示してくれているからです。特に「lintエラーにもならない」という点が厄介で、一見問題なく書けているように見えても、実行時に意図しない挙動になったり、そもそもスタイルが適用されなかったりといったことが起こりえます。このような実践的な知見は、学習コストを抑え、開発効率を上げる上で非常に役立ちます。React Nativeのバージョン5.0.0-prevというプレビュー版での情報も含まれており、最新動向を追っている方にも参考になるでしょう。クロスプラットフォーム開発の恩恵を最大限に享受しつつ、ネイティブ環境の特性を理解して適切に対応するための、Webエンジニア必携のガイドと言えるのではないでしょうか。

### WebForms.java 2.1 Is Here — Control the DOM from Java!

次に注目したいのは、Java開発者にとっては非常に刺激的なニュースかもしれません。「WebForms.java 2.1 Is Here — Control the DOM from Java!」という記事です。タイトルを見て「え、JavaからDOMを直接コントロールするの？ ReactとかVueなしで？」と驚いた方もいるんじゃないでしょうか。まさにその通り、この記事は、Javaの世界でフロントエンド開発の常識を覆すようなアプローチを提案するフレームワーク、WebForms Core (WFC) の最新バージョン2.1について紹介しています。

これまでのWeb開発では、Javaのようなサーバーサイド言語は主にHTMLを生成してブラウザに送り返すサーバーサイドレンダリング（SSR）が主流でした。あるいは、APIサーバーとして機能し、UIの描画はReactやVueといったJavaScript製のSPA（シングルページアプリケーション）フレームワークに任せるという分業体制が一般的でしたよね。しかし、WebForms Coreは、この常識に一石を投じます。そのコンセプトは、「Javaのサーバーサイドロジックから、直接ブラウザの既存DOMを操作する命令を送り、UIを動的に更新する」というものです。具体的には、サーバーとブラウザ間でWebSocketのような永続的な接続を確立し、ユーザーがブラウザで何らかのアクションを起こすと、そのイベント情報がサーバーのJavaアプリケーションに送信されます。Java側でビジネスロジックを処理した結果、DOMを操作するための軽量な命令（例えば、ある要素のテキストを変更する、新しい要素を追加する、CSSクラスを適用するなど）がブラウザに送られ、ブラウザの軽量なJavaScriptランタイムがその命令を受け取ってDOMを更新します。

これの何がすごいかというと、開発者がフロントエンドの複雑なJavaScriptフレームワークの学習や、TypeScriptでの型定義、ビルドツールチェーンの構築といった手間から解放される可能性がある点です。ほとんどすべてのアプリケーションロジックとUIの状態管理をサーバーサイドのJavaで一元的に行えるため、Javaエンジニアがフルスタック開発をよりシームレスに行えるようになります。ReactやVueのようなクライアントサイドで完結するフレームワークが主流の今、あえてサーバー主導のUIアプローチが再評価されつつあるという流れの一部と捉えることもできます。例えば、ElixirのPhoenix LiveViewやRailsのHotwireなども、同様にサーバーサイドからUIを動的に制御するアプローチを取っています。

もちろん、このアプローチにはトレードオフもあります。ユーザー操作のたびにサーバーとの通信が発生するため、ネットワークのレイテンシがユーザー体験に影響を与える可能性や、サーバー側の負荷が増大する可能性も考慮する必要があります。また、ReactやVueのような活発なエコシステムや豊富なコンポーネントライブラリがすぐに手に入るわけではありません。しかし、特定のビジネスロジックが複雑でサーバーサイドに集約したい場合や、既存のJava開発チームが効率的にWebアプリケーションを開発したい場合には、非常に魅力的な選択肢となるでしょう。ReactやVueが「当たり前」ではない、新たなWeb開発の可能性を感じさせる興味深いニュースですね。

### React Signup Flows Need a Small State Machine

さて、続いてはReact開発者にとって非常に実践的な話題です。「React Signup Flows Need a Small State Machine」という記事。サインアップフォームや設定画面など、一見シンプルに見えるUIでも、実際に実装しようとすると、複数の状態が絡み合って複雑になりがちですよね。例えば、メールアドレスのバリデーション、APIリクエスト中のローディング表示、エラーメッセージの表示、確認メールの再送ボタンの有効・無効化、さらにはユーザーがボタンを連打してしまったりといったケース。これらを`isLoading`、`isValid`、`isSubmitted`、`isError`といった複数のboolean型のフラグで管理しようとすると、すぐに状態の組み合わせが爆発してしまい、「`isLoading`が`true`なのに`isError`も`true`になっている」といった矛盾した状態に陥りがちです。

この記事では、このような複雑なUIの状態管理に対して、「小さな状態機械（Small State Machine）」を導入することを提案しています。状態機械とは、システムが取りうる「状態（State）」と、その状態間で「遷移（Transition）」を引き起こす「イベント（Event）」を明確に定義するモデルです。例えば、サインアップフォームのフローを考えてみましょう。最初は「`IDLE`（何もしていない）」状態から始まり、ユーザーが入力すると「`EDITING`（入力中）」状態へ。フォームを送信すると「`SUBMITTING`（送信中）」状態へ遷移し、APIからの応答に応じて「`SUCCESS`（成功）」または「`FAILURE`（失敗）」状態へと移ります。再送ボタンを押せば「`RESENDING_EMAIL`（メール再送中）」といった状態も考えられますね。

状態機械の最大の利点は、常に「一つの状態しかアクティブにならない」という排他性です。これにより、複数のbooleanフラグがそれぞれ独立して変更されることで発生する、矛盾した状態の組み合わせを根本的に排除できます。また、どのようなイベントが、どの状態からどの状態へ遷移させるのかが明確になるため、コードの可読性が格段に向上し、不具合の発生も抑えられます。テストもしやすくなりますし、新しい機能を追加する際も、既存の状態機械に新しい状態や遷移を追加する形で、安全に拡張していくことができます。

Reactで状態機械を実装する方法としては、複雑なものであればXStateのような専用ライブラリを使う手もありますが、この記事が「小さな」状態機械と強調していることから、`useReducer`フックを使ってシンプルに実装するアプローチが想定されているのかもしれません。`useReducer`は、現在の状態とアクションを受け取って新しい状態を返す「レデューサー関数」を定義することで、比較的簡単に状態機械的なロジックを実装できます。これにより、特に複雑なユーザーフローを持つUIにおいて、より堅牢で理解しやすいコードを書くことが可能になります。プロダクトの品質を高める上でも、ぜひ取り入れたいプラクティスの一つですね。

### HTMLを社内共有するサービスを、コードを読まずに作る - 1人で25万行を回す自動運用の記録

さて、今日の最後にご紹介するのは、非常に挑戦的なタイトルが目を引く記事です。「HTMLを社内共有するサービスを、コードを読まずに作る - 1人で25万行を回す自動運用の記録」。これ、最初は「本当にコードを読まずに開発できるのか！？」と驚かれた方も多いんじゃないでしょうか。記事の著者であるcojiさんは、社内向けにHTMLを安全に共有するWebサービス「Artifact Share」を、たった一人で開発・運用されています。しかも、開発開始から4ヶ月でTypeScriptコードが25万行を超え、マージしたPRは1,144本、Issueは777件に達しているという驚異的な数字です。

もちろん、この「コードを読まずに作る」というのは、文字通り一切コードを読まないということではありません。記事のサブタイトルにもあるように、「コードを読まないと決めたぼくが、何につまずき、どんな仕組みを足し、何を作りすぎて捨てたのか。その試行錯誤から残った、仕様と実装のレビューループの話」というのが本質です。つまり、人間が手動でコードを読み、レビューする労力を最小限に抑えつつ、高い品質と生産性を維持するための、徹底した自動化とプロセス構築の話なんですね。

では、一人でこれほどの規模のシステムを、短期間で、しかも「コードを読む労力を減らしながら」どうやって実現したのでしょうか。その鍵は、おそらく「コード生成」と「徹底した自動運用」にあると考えられます。APIスキーマからの型定義生成はもちろん、CRUD操作のボイラープレートコード、UIコンポーネントのテンプレートなど、定型的なコードは可能な限り自動生成しているのでしょう。これにより、手書きするコードの量を劇的に減らし、人間の介入が必要な部分を限定することができます。また、テスト、リンティング、デプロイといった開発プロセス全体が高度に自動化され、CI/CDパイプラインが完全に整備されていると推測できます。これにより、変更が加えられるたびに自動で品質チェックが行われ、デグレード（機能低下）を防ぐとともに、手動での確認作業のオーバーヘッドを最小限に抑えているはずです。

そして、記事が最も強調しているのが「仕様と実装のレビューループ」です。コード自体を詳細に読まずとも、仕様が適切に設計され、生成されたコードがその仕様を確実に満たしていることを確認する仕組みが確立されているということ。これは、おそらく、仕様記述言語（OpenAPIなど）や自動テスト、あるいは生成されるコードのAPIインターフェースの整合性をチェックするツールなどを用いて実現されているのでしょう。

なぜこの取り組みが重要かというと、現代のソフトウェア開発における生産性向上、特に限られたリソース、つまり少人数チームや個人開発者が、いかにして大規模かつ高品質なシステムを構築・運用していくか、という課題に対する具体的な解を示唆しているからです。コードの品質は、人間が隅々まで読むことだけで担保されるわけではなく、ツールや厳格なプロセスによっても高水準に保つことができる、という強力なメッセージです。開発者がコードを書くことに集中するだけでなく、コードを「生成するツール」や開発プロセスを「自動化する仕組み」そのものに投資することの重要性を再認識させられる、非常に示唆に富んだ記事でした。
