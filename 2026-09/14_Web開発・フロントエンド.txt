### AWS Lambda の90分タイムアウト検証

まず最初にご紹介するニュースはこちらです。「AWS Lambda の90分タイムアウト検証」。

皆さん、AWS Lambdaの実行時間、これまでは最大15分でしたよね。ところが、なんと2026年9月から、最大90分、つまり5,400秒まで拡張されました。これはサーバレスの世界にとっては非常に大きな変化なんですよ。記事では、この新しい90分タイムアウトが実際にどう動くのか、CDKを使って検証していますね。

このタイムアウト延長にはいくつか条件があります。一つは「Lambda Managed Instances (LMI)」上で動く関数であること。もう一つは「非同期呼び出し」、または「ESM（イベントソースマッピング）」経由の呼び出しであること。つまり、同期呼び出しはこれまで通り15分のままなんですね。LMIというのは、AWSが管理する、より安定した環境を提供するLambdaインスタンスのことで、これが長時間の実行を可能にしている技術的な背景にあると考えられます。非同期やESMによる呼び出しは、リクエスト元が関数の実行完了を待つ必要がないため、長時間かかる処理に適しているわけです。

では、なぜ今、AWSはこのタイミングでLambdaのタイムアウトを90分に延長したのでしょうか？これは、昨今のクラウドネイティブな開発トレンドと深く関わっています。これまで、動画のエンコードや大規模なデータ変換、機械学習のバッチ推論、あるいは複雑なレポート生成といった長時間かかる処理は、EC2インスタンスやECSコンテナのような、よりリソースが確保された環境で実行されることが多かったんです。しかし、Lambdaの実行時間が大幅に伸びたことで、これらのユースケースがサーバレスの恩恵を受けやすくなります。つまり、インフラの管理なしで、スケーラブルに、そしてイベント駆動でこれらの重い処理を実行できるようになるわけです。

エンジニアにとっては、これはアーキテクチャ設計の選択肢が大きく広がることを意味します。これまでだと、複数の短いLambda関数をAWS Step Functionsでオーケストレーションしたり、あるいはコンテナサービスを使うしかなかったような処理も、一つのLambda関数で完結できる可能性が出てきました。もちろん、長時間実行されるということはコストもそれなりにかかりますし、処理の冪等性（べきとうせい）やエラーハンドリングはこれまで以上に慎重に設計する必要があります。しかし、この変更はサーバレスアーキテクチャの適用範囲を確実に拡大する、非常に重要な一歩だと言えるでしょう。

### The Browser's Main Thread Is Expensive

続いてご紹介するのは、RedditのWeb開発コミュニティで話題になっていたこちらの記事です。「The Browser's Main Thread Is Expensive」。

これは、フロントエンド開発者にとって非常に耳の痛い、だけど避けては通れないテーマですね。ブラウザのメインスレッドがいかに高価であるか、そしてその扱い方を誤ると、ウェブサイトのパフォーマンスやユーザー体験にどれほど悪影響を及ぼすかについて解説しています。

ブラウザのメインスレッドは、ウェブページの表示において、ほとんどの重要なタスクを担っています。具体的には、JavaScriptの実行、HTMLのパース、CSSのスタイル計算、レイアウトの構築、そして最終的なピクセルの描画といった処理です。さらに、クリックやスクロールといったユーザーの入力イベントの処理もメインスレッドが行っています。

このメインスレッドがJavaScriptの重い処理などでブロックされてしまうと、ユーザーがボタンをクリックしても反応が遅れたり、アニメーションがカクついたり、ひどい場合にはページ全体がフリーズしたように見えたりします。これは、Web Vitals、特に「FID (First Input Delay)」や「LCP (Largest Contentful Paint)」といったユーザー体験を測る重要な指標にも直結します。FIDはユーザーが最初にページを操作しようとした時に、ブラウザがどれだけ早く反応できたかを示す指標で、メインスレッドがブロックされているとこれが悪化しますし、LCPはページの一番大きなコンテンツが表示されるまでの時間なので、ここもメインスレッドの負荷が影響します。

では、どうすればメインスレッドの負担を減らせるのでしょうか？記事でも述べられているように、いくつかのベストプラクティスがあります。例えば、重いJavaScriptの処理を小さなチャンクに分割して、ブラウザがアイドル状態の時に実行するようにスケジューリングしたり、Web Workersを使って、UIとは独立したバックグラウンドスレッドで計算量の多い処理を実行させたりする方法があります。これにより、メインスレッドを解放して、UIの応答性を保つことができます。その他にも、リストの仮想化（ウィンドウ処理）で一度に表示する要素数を減らしたり、不要なJavaScriptのバンドルサイズを削減したり、画像の遅延読み込みを適切に行うことも重要です。CSSのアニメーションも、`transform`プロパティのようにメインスレッドへの負荷が少ないものを選ぶといった工夫も求められます。

ウェブサイトのパフォーマンスは、もはや「あれば嬉しい」というレベルではなく、ビジネスの成功に直結する重要な要素です。フロントエンドエンジニアは、見た目を美しくするだけでなく、その裏側でいかに快適に動かすか、という点にも深く責任を持つ必要があるということですね。パフォーマンスは、立派な機能の一つなんです。

### ローカルLLMにレビューさせていた話の続報（前回の構成、実は動いていませんでした）

次にピックアップするのは、Zennで公開されたこちらの記事です。「ローカルLLMにレビューさせていた話の続報（前回の構成、実は動いていませんでした）」。

これは、前回の記事で紹介した「トークンを節約するためにローカルLLMでコードレビューをさせていた話」の続報なんですが、なんと、その構成に重大な不備があり、実はうまく動いていなかった、という率直な告白の記事なんです。驚きですよね。

著者は、Ollamaというツールを使ってローカルでLLM、具体的にはqwen2.5-coder:14bというモデルを動かし、Modelfileという設定ファイルでシステムプロンプトをカスタマイズしてコードレビューさせていたそうです。ところが、記事を読んだ方からの指摘で、ModelfileのシステムプロンプトがOllamaの`/api/chat`エンドポイントでは正しく適用されていなかったことが判明したと。つまり、期待していたようなレビューは行われておらず、トークンを節約できていたと思っていたのも勘違いだった、というわけです。

この話、私たちエンジニアにとっては非常に示唆に富んでいます。LLMを開発ワークフローに組み込むというのは新しい試みであり、その設定や挙動にはまだ未知の部分が多いという現実を突きつけられます。特に、今回のように「サイレントエラー」、つまりエラーとして検知されずに、ただ期待通りに動いていない、という状況は一番厄介です。LLMの応答自体はそれなりに賢く見えてしまうので、「動いている」と錯覚しやすいんですよね。

この事例から学べるのは、新しいツールやAPIを使う際は、その内部挙動や設定の適用ルールを深く理解する必要があるということ。そして、「動いているように見える」だけでは安心せず、本当に意図通りに機能しているか、具体的なテストや検証を怠らないことの重要性です。LLMのようなブラックボックス性の高い技術であれば、なおさらデバッグの難易度も上がりますからね。

著者が正直に「実は動いていませんでした」と公開してくれたことは、コミュニティにとって非常に価値があります。これは失敗を隠さずに共有し、そこからみんなで学ぶ、というエンジニアリング文化の良い例だと思います。私たちも、新しい技術に飛びつく際には、その裏側にある技術的な詳細を理解し、謙虚な姿勢で検証を重ねていく必要がある、ということを改めて教えてくれるニュースでした。

### I was tired of ad-filled "What is my IP" sites, so I built an open-source one with Cloudflare Workers

次に注目するのは、開発者が個人的な不満を最新技術で解決した、という爽快なニュースです。「I was tired of ad-filled "What is my IP" sites, so I built an open-source one with Cloudflare Workers」。

皆さんも経験ありませんか？VPNをオンにした後やプロキシ設定を変更した時に、「自分のIPアドレスって今どうなってるんだろう？」と思って、Googleで「what is my IP」と検索すること。そして、その結果出てくるサイトのほとんどが、大量のバナー広告、しつこいポップアップ、そして個人情報収集のためのトラッキングスクリプトで溢れかえっている、という状況に。しかも、表示される位置情報が間違っていることも少なくない、と。この記事の著者は、そんな状況に嫌気がさして、自分でシンプルでクリーンなツール「My-IP-Info」をCloudflare Workersを使って構築した、という話なんです。

これ、まさに「エンジニアあるある」で共感する方も多いのではないでしょうか。そして、この問題を解決するためにCloudflare Workersを選んだ、というのがポイントです。Cloudflare Workersは、Cloudflareの広大なグローバルエッジネットワーク上で動作するサーバレスプラットフォームです。つまり、コードがユーザーに地理的に近い場所で実行されるため、非常に低遅延で高速な応答を実現できます。加えて、スケーラビリティも高く、運用の手間もほとんどかかりません。

「自分のIPアドレス」を確認する、というシンプルな機能であれば、重厚なバックエンドサーバは不要です。Cloudflare Workersは、ユーザーからのリクエストがCloudflareのエッジサーバーに到達した時点で、そのリクエストのヘッダー情報（例えば`CF-Connecting-IP`ヘッダーなど）からクライアントのIPアドレスを読み取り、それをすぐに返すことができます。余計な処理がないため、高速かつシンプルに機能を提供できるわけです。しかも、著者はこれをオープンソースで公開しています。これにより、透明性が確保され、広告やトラッキングがない、信頼できるツールとして多くの人に使ってもらえるようになるでしょう。

このニュースは、現代のウェブ開発において、エッジコンピューティングがいかに身近で強力なツールになっているかを端的に示しています。些細な不満から生まれた個人的なプロジェクトが、最新技術の活用によって、多くのユーザーの利便性を高めることができる好例ですね。私たち開発者も、日々の「これ、もっと良くなるのに」という感覚を大切にして、積極的に新しい技術を試していくべきだと感じさせてくれる話でした。

### Beyond a Basic Weather App: Architecture & Resilience in React

さて、Web開発、特にフロントエンドの話題として、Reactに関するものも見ていきましょう。こちらの記事です。「Beyond a Basic Weather App: Architecture & Resilience in React」。

Reactの学習を始めたばかりの皆さんなら、一度は「天気予報アプリ」を作ったことがあるかもしれません。APIから天気データを取ってきて、UIに表示する、というシンプルなプロジェクトですね。しかし、この記事の著者は言います。「天気予報アプリはシンプルなチュートリアルプロジェクトと見なされがちだが、それを回復力のある、本番環境に対応したシステムに変えるには、現実世界のフロントエンドの課題を解決する必要がある」と。これは、まさに「動く」から「プロとして使う」レベルへ、フロントエンド開発を一段階引き上げるための非常に重要な視点を提供してくれています。

では、具体的に「堅牢で回復力のあるReactアプリケーション」を構築するためには、どんなアーキテクチャや技術的考慮が必要なのでしょうか。記事ではいくつかのポイントが挙げられています。

まず「エラーバウンダリー（Error Boundaries）」。これはReactの機能で、コンポーネントツリー内で発生したJavaScriptエラーをキャッチし、アプリケーション全体がクラッシュするのを防ぎつつ、代替のUIを表示するためのものです。これにより、ユーザー体験が完全に損なわれるのを防ぎます。

次に「堅牢な状態管理」。ただ`useState`を使うだけでなく、アプリケーション全体で共有する状態については、Context APIやRedux、Zustandといったライブラリを適切に使い分け、データのローディング中、エラー発生時、成功時といった状態をきちんと管理することが求められます。

さらに「データフェッチングとキャッシング」。React Query（TanStack Query）やSWRのようなライブラリを使って、効率的なデータ取得、再検証、そしてキャッシュを行うことで、ユーザーはより高速で快適な体験を得られます。これにより、ネットワークリクエストの頻度を抑え、パフォーマンスを向上させることができます。

他にも、UIを小さな再利用可能なコンポーネントに分割する「コンポーネント設計」、アプリケーションの品質を保証するための「テスト戦略」、そして全てのユーザーが使えるようにするための「アクセシビリティ（A11y）」への配慮、さらに「パフォーマンス最適化」のためのメモ化や仮想化など、挙げればキリがありません。

これらの要素は、単にコードを書くだけでなく、「設計」という視点からフロントエンドアプリケーションを捉えることの重要性を示しています。チュートリアルを終えたばかりの学生さんや、若手エンジニアにとっては、次のステップに進むための非常に具体的なガイドラインとなるでしょう。プロフェッショナルなフロントエンド開発者として、スケーラブルで保守性の高いコードを書くためには、これらの知識が不可欠だということですね。
