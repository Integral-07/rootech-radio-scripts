### Claude reveals ECDSA curve origins

**須藤:** 今週のAI関連のニュースで、もう一つ非常に興味深い発見がありました。またしてもAnthropicのAI「Claude 3 Opus」が絡む話なんですが、今回は暗号技術の世界に足を踏み入れています。「ECDSA」という楕円曲線デジタル署名アルゴリズムで使われる、ある「秘密の種」の起源を、Claudeが解明したというんです。

ECDSAは、皆さんのデジタル署名、ブロックチェーン、セキュアブートなど、現代のセキュリティを支える非常に重要な暗号アルゴリズムです。このECDSAで使われる標準的な楕円曲線、特にNIST Pカーブ（P-256、P-384など）というものには、その定義の一部に「何も隠されていない」ことを示すための、いわゆる「nothing up my sleeve numbers」という一見ランダムに見える数字が含まれていました。しかし、この「種（シード）」がどうやって生成されたのか、その具体的な方法が長い間謎とされてきたんです。

この謎は、特にエドワード・スノーデン氏の暴露以降、NSA（アメリカ国家安全保障局）が暗号標準にバックドアを仕込んでいるのではないかという疑惑と結びつき、大きな懸念材料となっていました。もしこの「種」が本当にランダムではなく、特定の意図を持って生成されていたとしたら、NSAだけがその秘密を知っていて、簡単に署名を破ることができてしまう可能性があったからです。

そこに登場したのが、Claude 3 Opusです。Claudeは、これらの「種」の値だけを手掛かりに、その生成方法を突き止めたのです。具体的には、P-256などのシンプルな文字列を繰り返しハッシュ化し、そのハッシュ出力の一部を「種」として使うという、そのロジックを正確に推測しました。つまり、「種」は暗号学的に見て真にランダムではなかったものの、悪意のあるバックドアではなく、単にその生成プロセスが公開されていなかっただけだった、ということが判明したわけです。

この発見の意義は非常に大きいです。
まず、長年の疑念が晴れて、NIST Pカーブの信頼性が大きく向上したこと。これは暗号コミュニティにとって大きな安心材料です。
そして何より、AIが科学的発見に貢献できる可能性を鮮やかに示しました。Claudeは、この問題のために特別に訓練されたわけではないにも関わらず、高度な記号推論とパターン認識能力を駆使して、専門家でも長年解けなかった謎を解明したんです。これは、AIが今後の科学研究や、複雑なシステム、あるいはコードのデバッグなど、さまざまな分野で強力なアシスタントになりうることを示唆しています。人間の専門家であるフィリッポ・ヴァルソルダ氏がClaudeの結果を独自に検証したことで、その信頼性もさらに高まりましたね。AIの進化が、まさに歴史的な謎を解き明かす一助となる、そんな時代になったことを感じさせるニュースでした。

### Learned Index Lab: Replacing B-Trees with streaming linear models in pure Rust (-99% RAM, 3x faster)

**須藤:** さて、今度はデータ構造とパフォーマンスの話に移りましょう。「Learned Index Lab」というプロジェクトが、データベースのインデックスに使われる伝統的なB-Treeを、ストリーミング線形モデル（streaming linear models）に置き換えることで、RAM消費量を99%削減し、処理速度を3倍に高速化した、という驚きの発表がありました。しかも、純粋なRustで実装されているというんですから、これはエンジニアとしては見逃せません。

B-Treeは、データベースのインデックスとして何十年も使われてきた、非常に確立されたデータ構造です。データをソートされた順序で保存し、ポインタを辿ってノードを移動することで、効率的な検索、挿入、削除を実現します。しかし、このポインタを辿るという処理は、メモリのキャッシュミスを引き起こしやすく、特にデータ量が増えると性能のボトルネックになることがありました。

それに対して「Learned Index」（学習型インデックス）というのは、機械学習モデルを使って、キーがデータ配列のどこにあるかを予測する、という新しいアプローチです。インデックスそのものを、キーと位置をマッピングする「モデル」と捉えるわけですね。

今回のLearned Index Labの実装では、「ストリーミング区分線形回帰」（streaming piecewise linear regression）という手法を使っています。これは、複雑で不均一なデータ分布に対しても、データストリームに沿って複数の線形モデル（直線）を当てはめていくことで、キーの分布をリアルタイムに学習するというものです。

では、どうやって高速化と省メモリを実現しているのでしょうか？
まず、RAMの99%削減というのは、B-Treeが大量のノードやポインタを明示的に保持するのに対し、学習型インデックスはキー分布を表現するコンパクトなモデル（線形セグメントのパラメータなど）しか持たないためです。これにより、より多くのインデックスデータをメインメモリやキャッシュに収めることが可能になります。
そして、3倍の高速化は、モデルがキーの位置をCPUのALU（算術論理演算ユニット）で直接計算できるため、ポインタチェイシングやキャッシュミスの回数が劇的に減るからです。予測された位置の周辺をごくわずかな範囲だけ検索すれば良いので、非常に高速なルックアップが可能になるわけです。

このプロジェクトがRustで実装されている点も注目です。Rustはメモリ安全性と高いパフォーマンスを両立できるシステムプログラミング言語です。C/C++に近い低レベルな制御が可能でありながら、安全性を保証するコンパイラチェックがあるため、このようなメモリ効率と速度が求められるデータ構造の実装に非常に適しています。

もちろん、学習型インデックスにはまだ課題もあります。特に、データの更新（挿入や削除）があった場合に、モデルの一部を再学習したり再構築したりする必要があるため、読み込みが多いワークロードに向いていると言われています。しかし、これはデータベースのインデックス技術における大きな進歩であり、将来的にはより高速で省リソースなデータベースの実現に繋がる可能性を秘めています。システムエンジニアやデータベース開発者にとっては、この新しいパラダイムが実務にどう影響してくるか、注視していく必要がありますね。

### Learning Postgres extensions using Zig

**須藤:** 続いては、プログラミング言語のトレンドとデータベース技術が交差するニュースです。「PostgreSQL」の拡張機能を「Zig」という比較的新しい言語で開発する方法が紹介されていました。

PostgreSQLは、その堅牢性と拡張性の高さで非常に人気のあるリレーショナルデータベースです。ユーザーは、C言語を使ってカスタム関数やデータ型、さらには独自のインデックスアクセス方式まで、さまざまな拡張機能を書くことができます。Postgres自体がC言語で書かれていて、C言語の安定したAPIを提供しているため、C言語が拡張機能開発のデファクトスタンダードとなっています。

そこに登場するのが、Zigです。Zigは、C/C++に代わる「次世代のシステムプログラミング言語」として注目を集めています。その特徴はいくつかありますが、特にPostgres拡張機能の開発において有利な点がいくつか挙げられます。
一つ目は、「C言語との優れた相互運用性」です。ZigはCのライブラリやAPIを非常にシームレスに呼び出すことができ、CベースのPostgresコードベースと深く連携させるのが非常に簡単です。これは、RustがCとの連携にFFI（Foreign Function Interface）のボイラープレートを多く必要とするのと比較して、大きな利点と言えます。
二つ目は、「低レベルな制御」が可能であること。C言語と同様に、メモリやCPUに対して細やかな制御ができるため、データベース操作のようなパフォーマンスが重視される場面でC言語並みの速度を実現できます。
三つ目は、「メモリ安全性」に関するサポートです。ZigはC言語のような手動メモリ管理を許容しつつも、デバッグモードでは use-after-free やメモリリークといったC言語でよくあるバグをコンパイル時に検出する機能を提供しています。これは開発者の生産性とコードの堅牢性を高める上で非常に重要です。

なぜZigを使ってPostgres拡張機能を作るのが良いのか？それは、C言語が持つパフォーマンスと低レベルな制御という利点を享受しつつ、よりモダンな構文、優れたツールチェイン、そしてより安全な開発体験を提供してくれるからです。記事では、純粋なC言語で書くよりも、Zigを使うことで開発プロセスが簡素化されつつも、Postgresの内部構造に直接アクセスできる点が強調されていました。

これは、システムプログラミングの分野で、C/C++の牙城を崩そうとするZig（やRust）のような新興言語の勢いを示すものです。データベース開発者にとって、Zigは堅牢で高性能なPostgres拡張機能を、より効率的かつ安全に構築するための魅力的な選択肢となり得るでしょう。

### Stop Failing Pipelines: Implementing Quarantine Gates in Delta Live Tables

**須藤:** 最後に、データエンジニアリングの分野から、データ品質（データクオリティ）に関する非常に実用的なニュースをご紹介します。「Delta Live Tables」（デルタライブテーブル）で「Quarantine Gates」（隔離ゲート）を実装することで、データパイプラインの停止を防ぐ方法についてです。

データパイプラインは、データを移動・変換する上で不可欠なものですが、「汚れたデータ」、つまり品質の低いデータが混入すると、分析結果の誤り、コンプライアンス違反、さらにはAIモデルの性能低下など、深刻な問題を引き起こします。

これまでのデータ品質チェックで問題が見つかった場合、伝統的なアプローチでは「パイプライン全体を停止させる」ことが一般的でした。これは、問題のあるデータが下流システムに流れるのを防ぐための確実な方法ですが、運用上の大きな混乱や遅延、再処理コストを発生させるという問題がありました。記事の筆者は、特に重要なシステムにおいて、この「パイプラインを停止させる」という考え方を「根本的に間違っている」とまで言い切っています。

そこで提案されているのが「Quarantine Gates」、つまり「隔離ゲート」です。これはDatabricksが提供するデータパイプライン構築フレームワークであるDelta Live Tables（DLT）の機能を使って実装されます。
この隔離ゲートの仕組みはこうです。データが定義された品質要件（例えば「このカラムはNULLであってはならない」とか「値がこの範囲内に収まっているべき」といった制約）を満たさなかった場合、その「問題のあるデータ」だけを、パイプラインのメインストリームから切り離し、別の「隔離（クアランティン）テーブル」やストレージ領域に移動させるのです。
一方で、品質要件を満たした「良いデータ」は、そのままパイプラインを流れ続け、下流のシステムへと届けられます。

このアプローチのメリットは非常に大きいです。
まず、「本番環境の安定性」が確保されます。一時的なデータの問題や、特定の部分的なデータエラーによってパイプライン全体が停止することがなくなり、ダウンストリームのシステムは常に有効なデータを受け取り続けられます。
次に、「迅速な修正」が可能になります。データエンジニアは、隔離されたデータを調査し、問題の根本原因を特定して、データを修正し、後から独立して再処理することができます。この間、メインのパイプラインは停止しません。
そして、最終的な「データ整合性」は保ちつつ、より回復力のある方法でデータを供給できるわけです。また、パイプライン全体の再実行という高コストな処理を避けることで、「コスト効率」も向上します。

Delta Live Tablesでは、SQLやPythonを使ってデータ品質の期待値（`EXPECT (col IS NOT NULL)` のような制約）を簡単に定義でき、さらにその失敗時の挙動を `FAIL`（停止）、`DROP`（破棄）、そして `QUARANTINE`（隔離）の中から選択できる機能があります。

この「隔離ゲート」の導入は、特にHIPAAやPCIなどの規制要件が厳しい業界において、データ品質を保証しつつ、システムの運用安定性を高めるための成熟したアプローチと言えます。データエンジニアの皆さんにとっては、このようなパターンを導入することで、より堅牢で信頼性の高いデータプラットフォームを構築するための重要なヒントになるはずです。
